# REDCap Enrolment Workflow

This document describes the current intended REDCap enrolment workflow for ADIMAGENDO Study Buddy.

## Core principle

`studyRecordId` is the authoritative research identity.

It comes from the REDCap `record_id` and binds:
- the REDCap participant record,
- the generated enrolment / magic link,
- the participant app account,
- the participant profile in the app.

App login email is an authentication credential only. It may differ from the REDCap email on file and must not be used as the stable research identifier.

## Current workflow

1. A participant becomes eligible / consented in REDCap.
2. REDCap sync imports eligible baseline records into the app.
3. The app stores synced REDCap records keyed by `studyRecordId`.
4. A study coordinator uses the admin dashboard to generate an enrolment link for a `studyRecordId`.
5. The system creates an enrolment token / magic link.
6. The participant opens the magic link.
7. The enrolment page checks that the token exists, is not expired, is not revoked, and is not already used.
8. The participant enters their date of birth for verification.
9. The app compares the submitted DoB against the synced REDCap DoB.
10. If DoB verification fails, the token must not be consumed. The participant must be able to retry with the correct DoB.
11. If DoB verification succeeds, the participant registers using their preferred app login email and password.
12. The app creates the participant user account and participant profile.
13. The participant profile is linked to the REDCap record by `studyRecordId`.
14. The participant is signed in and can access the participant dashboard.
15. The admin dashboard should reflect the updated enrolment / account activation status.

## Important identity rules

- `studyRecordId` is the single stable research identity.
- REDCap email is informational / contact-related.
- App login email is authentication only.
- App login email may differ from REDCap email.
- Do not link participant research data by email.
- Do not accept client-provided `studyRecordId` during registration.
- The `studyRecordId` used during registration must come from the server-side enrolment token flow.

## Magic link rules

- Magic links are generated by the admin workflow.
- A generated link should be tied to a `studyRecordId`.
- A failed DoB verification must not consume the token.
- `usedAt` should only be set after successful DoB verification and successful account/profile creation.
- Regenerating a link should make the active-link state clear to admins.
- Already-bound records should not be silently overwritten or re-linked.

## Consent and enrolment date rules

- Consent eligibility comes from REDCap sync.
- Enrolment date should come from REDCap consent date logic, not from app signup time.
- For under-18 participants, enrolment date should reflect the required participant and parent consent logic.
- Participant profile enrolment dates should remain consistent with synced REDCap consent data.

## Admin dashboard expectations

The admin dashboard should help study coordinators understand:
- whether a participant has a synced REDCap record,
- whether an enrolment link has been generated,
- whether a link is active, expired, or already used,
- whether the app account has been activated,
- whether app login email differs from REDCap email.

## Safety rules

- Use synthetic test data only.
- Do not expose real participant email, DoB, REDCap record ID, consent dates, uploads, or contact messages.
- Do not use production REDCap data for local testing.
- Do not log sensitive participant identifiers in debug output.
- Do not modify production REDCap integration without explicit human approval.

## Known watch points

- Manual link generation for a non-synced `studyRecordId` may be risky.
- REDCap sync classification and consent-date logic need strong tests.
- DoB timezone handling should be checked carefully.
- Token regeneration behavior should be tested.
- Admin status aggregation should be tested.
- Email mismatch UI should be tested.
- Checklist progress depends on the hardcoded `ADMIN_CHECKLIST_STEP_TOTAL` in `src/lib/admin/checklist-progress.ts`.
